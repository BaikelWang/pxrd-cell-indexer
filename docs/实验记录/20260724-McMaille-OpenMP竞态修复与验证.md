# 2026-07-24 — McMaille OpenMP 竞态根因定位与修复（方案 B 落地）

> **背景**：`20260724-McMaille-OpenMP竞态问题实测.md` 证明「直接加 `-fopenmp`」不安全。
> 本记录做的是：**找到真正的竞态根因（不是之前猜测的 `NOUT`），设计最小改动修复，并用重复实验验证「零精度损失、真实加速」。**

---

## 结论先行

- 真正的竞态源不是 `NOUT`（它在全部 6 个晶系并行块里其实早已正确声明为 `FIRSTPRIVATE`），
  而是全局候选槮位计数器 **`IGC`** 在三段**互不互斥**的命名 critical
  （`STORE1`→非临界代码→`STORE2`→非临界代码→`FOUND`）之间被**乱序读写**：
  一个线程在 `STORE1` 里拿到 `IGC=5` 存了候选，退出临界区后，在等它进 `FOUND` 之前，
  另一个线程可能已经把共享 `IGC` 推进到 6、7…；原线程在 `FOUND` 里再用共享 `IGC`
  去查 `RP(IGC)`、做「去重合并」时，读到的已经是**别的线程的槮位**——这正是候选表里
  出现 `F.o.M.=Infinity`、`NaN` 的根因。
- **修复**：把 `STORE1`/`STORE2`/`FOUND` 三段合并成**一个连续的 critical 区域**
  （不是简单改名字，是删掉中间的 `END CRITICAL...CRITICAL` 边界），让"发布一个候选 +
  去重合并"这件事在多线程下也保持和单线程完全一致的"不可分割"语义。
  这段代码只在极少数命中候选门槮（`RMAX0`/`IPEN` 等）时才执行，不在
  每次 MC 试探都跑的热路径（`CALCUL1`，其 `/CAL/` 早已是 `THREADPRIVATE`）上，
  所以对可并行度几乎没有影响。
- **验证**：`000001`（SnSe）样本，5 次重跑（16×3、32×1、64×1 线程）：
  - **零 NaN / Infinity**，候选表全部合法；
  - **总计算量没被截断**：`totCPU` 稳定在 634.8–692.5 s，与原单线程基线 676.7 s 一致；
  - **墙钟时间**：16 线程 ~48–50 s（~13.5×），32/64 线程 ~38.7 s（~17.5×，出现扩展性平台）；
  - **正确性**：5 次里 2 次精确命中最小晶胞（与 CIF 真解一致，McM20 52.8–54.6，
    略优于原基线的 52.75），3 次命中同一"胞族"里的等价倍胞候选（McM20 37.3 左右，
    与原单线程基线候选表 rank-2 完全一致）——这是 McMaille 本身「墙钟时间做种」带来的
    固有 MC 随机性，与原单线程基线换种子重跑会出现的波动性质相同，不是并行引入的新问题。

## 根因定位过程

### 第一次尝试（失败）：只统一命名，不合并区域

先假设"只要把三个 critical 名字统一成同一个锁"就够了：

```bash
sed -i -e 's/CRITICAL(STORE1)/CRITICAL(CANDBOOK)/g' \
       -e 's/CRITICAL (STORE1)/CRITICAL(CANDBOOK)/g' \
       -e 's/CRITICAL(STORE2)/CRITICAL(CANDBOOK)/g' \
       -e 's/CRITICAL(FOUND)/CRITICAL(CANDBOOK)/g' \
       McMaille_omp_fixed.for
```

重新编译、跑 16 线程 ×3，结果**仍然是错的**：三次墙钟分别 2.0 s / 2.6 s / 13.5 s（严重不一致），
且候选表里仍然出现 `F.o.M.=Infinity`、`P`（无 Bravais 标注）等corrupted 行。

**原因**：三段 critical 在代码里本来就是**顺序执行、从不互相嵌套**的（`STORE1` 结束后才开始
`STORE2`，`STORE2` 结束后才开始 `FOUND`），单纯统一名字确实消除了"跨临界区互斥"问题，
但中间那两段**非临界代码区间**（准备 `CELPRE`/`BB`/`AFI` 等，各约 10~25 行）仍然给了
其他线程"插队"修改共享 `IGC` 的窗口——`STORE2`/`FOUND` 里继续用共享 `IGC` 当索引，
读到的可能已经是别的线程刚抢先递增的新槮位。

### 第二次尝试（成功）：删除中间边界，合并成一个连续临界区

对每个晶系的 6 个并行块，各删除 4 行（两对 `END CRITICAL(...)` + `CRITICAL(...)`），
只保留最外层的一个 `START` 和一个 `END`：

```python
lines_to_delete = {838,850,874,899, 1268,1280,1304,1329, 1681,1693,1717,1742,
                    2146,2158,2182,2207, 2637,2650,2674,2700, 3172,3187,3212,3240}
# 立方 / 六方三方菱方 / 四方 / 正交 / 单斜 / 三斜，每晶系 4 行
```

即从「拿到 `IGC` 那一刻」到「去重合并逻辑结束」整段，在多线程下也强制串行，
和单线程执行时天然的顺序语义完全一致。

## 编译与测试

```bash
cd third_party/McMaille/run_lab
gfortran -O3 -fopenmp -ffixed-line-length-132 -std=legacy -fallow-argument-mismatch \
  -o mcmaille_omp_fixed McMaille_omp_fixed.for

cd omp_fixed_test_000001
OMP_NUM_THREADS=16 ./mcmaille_omp_fixed 000001b   # ×3
OMP_NUM_THREADS=32 ./mcmaille_omp_fixed 000001b   # ×1
OMP_NUM_THREADS=64 ./mcmaille_omp_fixed 000001b   # ×1
```

| 16（run1） | 50.3 s | 641.2 s | a=11.513,b=4.170,c=4.424,McM20=**54.55** | ✅ |
| 16（run2） | 47.8 s | 636.0 s | a=11.513,b=3.513,c=6.020,McM20=37.34 | 等价倍胞（=原基线 rank-2） |
| 16（run3） | 49.7 s | 634.8 s | a=11.513,b=4.427,c=4.167,McM20=52.79 | ✅（轴标签置换） |
| 32 | 38.7 s | 659.6 s | a=11.513,b=6.022,c=3.513,McM20=37.34 | 等价倍胞 |
| 64 | 38.7 s | 692.5 s | a=11.513,b=6.022,c=3.513,McM20=37.36 | 等价倍胞 |

- 32/64 线程墙钟基本打平（~38.7 s），说明在本机（180 核，但很可能受锁竞争 /
  `OMP DO` 静态调度负载不均 / NUMA 影响）上加速比在 ~16-32 线程区间就到了平台，
  继续加线程收益有限——**不是又退化，是 Amdahl 效应**（totCPU 仍然完整，
  只是候选发布临界区在线程数更高时排队变多）。
- 16 线程是目前实测「加速比 / 线程占用」性价比最高的档位（~13.5×，totCPU 完整）。

## 对「不影响精度」结论的诚实边界

1. 这次验证只用了 `000001`（SnSe，正交，20 峰）一个样本，且只跑了 5 次重复。
   **在推广为默认加速手段之前，必须在已知真值回归集（`y2o3b`/`PBSO4`/`000001` 等）上
   做多次重跑的一致性验证**，尤其要覆盖单斜/三斜真解样本（本次样本的真解是正交，
   还没验证过「真解本身就是单斜」时这个修复是否同样稳。
2. Top-1 候选在不同线程数/不同次重跑之间出现「精确最小晶胞」vs「等价倍胞」的摇摆，
   这是 McMaille 用墙钟时间播种 MC 的固有行为，原单线程基线换个时间点重跑也会摇摆——
   这不是本次修复引入的新风险，但意味着「单次跑出的 Top-1」本身就不该被当成
   100% 确定性输出，无论并行与否。
3. 尚未验证候选发布路径之外是否还有其他未审查的共享状态（比如 `CELREF`/`CELREF2`
   内部是否有游离于 `/CAL/`、`/CAL2/` COPYIN 范围之外的隐藏全局状态）——本次修复
   针对的是**已定位、已复现**的这一个根因，不代表"审计完毕"。
